eurohpc-qdevices user manual¶

Use eurohpc-qdevices to send a fixed list of circuits to a EuroHPC quantum computer, one job at a time, with an exact record of what was sent and what came back. It is for holders of a EuroHPC quantum award, on a laptop or a login node:

  • Euro-Q-Exa at LRZ, through the Munich Quantum Portal;

  • VLQ at IT4Innovations, through LEXIS and HEAppE;

  • Piast-Q at PCSS, through the PCSS broker.

See also

To get onto the machines, follow the ENCCS lesson EuroHPC JU quantum devices and HPC-QC access in practice: applying, onboarding at each site, and a first job on each machine. This manual covers the app only.

Package eurohpc-qdevices, import name qdevices, command qdevices. Start with Install and first run, and read Live runs before a live run.

Status. The app has run live on each of the three machines. The offline tests run against fake sites.

What it does, and what it does not¶

It reads a manifest, checks it offline, reads the state of a machine, sends the jobs in order with a record synced to disk, collects jobs after a crash, records your decision on an order with qdevices resolve, stops on rules, and shows runs, jobs and usage from the records.

It does not build, compile, emulate or change circuits: the text in the file is sent unchanged. It holds no rule of an experiment: give those in a Python file. It never cancels a job, never sends a lost submission again, and never stores or prints a token.

You need:

  • a EuroHPC quantum award, and an account at the site of the machine (the lesson shows how);

  • circuits in the form the site takes: OpenQASM for Euro-Q-Exa and VLQ, the broker’s operation list for Piast-Q;

  • the command line, and pixi or another Python package manager.

Install and first run¶

Install the app, then send one job. The app needs Python 3.11 or newer, with httpx and cryptography, which come with it. It needs no client library of a site. A VLQ token still needs a LEXIS login (VLQ (IT4Innovations)).

Install¶

With pixi, in a folder next to your manifests. A PyPI package needs Python from conda-forge in the project first:

pixi init my-runs && cd my-runs
pixi add "python=3.12"
pixi add --pypi "eurohpc-qdevices @ git+https://github.com/ENCCS/eurohpc-qdevices"
pixi run qdevices --help

For a clone, give its absolute path with --editable:

pixi add --pypi --editable "eurohpc-qdevices @ file:///absolute/path/to/eurohpc-qdevices"

Once it is on PyPI, pip install eurohpc-qdevices in a virtual environment works too. Check the install with pixi run qdevices --version. Below, qdevices means pixi run qdevices, or qdevices inside pixi shell.

First run¶

Read Live runs and the page of your site first. These steps send one job to Euro-Q-Exa with examples/euroqexa-one-qubit. For VLQ and Piast-Q, change the site name and the token variable.

  1. Copy examples/qdevices.toml to ~/.config/qdevices/qdevices.toml. Put your project in place of MY-PROJECT there and in the manifest (Configuration, Manifests and records).

  2. Run the commands below. FILE is a file of your own that holds the token (Tokens).

  3. With several jobs, look at the first, then go on with qdevices send MANIFEST --live --resume RECORD --max-order N (Commands).

qdevices dry-run examples/euroqexa-one-qubit/manifest.json    # offline, no token: "Dry run passed. Nothing was sent."
qdevices login euroqexa                                       # how to get the token, and the variable to set
set +x; export MQSS_TOKEN="$(cat FILE)"                       # LEXIS_TOKEN for VLQ, PCSS_API_KEY for Piast-Q
qdevices check euroqexa --live --manifest examples/euroqexa-one-qubit/manifest.json   # one read, stored; no job
qdevices dry-run examples/euroqexa-one-qubit/manifest.json    # again: the qubits against the read, and its age
qdevices send examples/euroqexa-one-qubit/manifest.json --live --max-order 1   # the first job alone
qdevices runs                                                 # one line for each record: find the record here
qdevices jobs RECORD                                          # one line for each order
qdevices usage                                                # totals by site and project

With no_modify, the second dry run also checks the gate names and the coupled pairs (Euro-Q-Exa (LRZ)). The send prints the path of the record, then each step. Step 1 edits these two files:

send¶

qdevices send MANIFEST --live --max-order N                 # a new record: send the orders 1 to N
qdevices send MANIFEST --live --resume RECORD --max-order N # go on with a record, up to order N
qdevices send MANIFEST --live --resume RECORD               # collect only: no new job
qdevices send MANIFEST --live --max-order N --new-run       # a new record that sends the first orders again
qdevices send MANIFEST --live --max-order N --rules FILE    # with the rules of an experiment

Each call reads the machine once, runs the rules on that read and checks every job against it (Rules); a run sent in stages gets a new read at each call. Then each order goes as the figure above shows (Live runs): a final order is never sent again, an open order is collected, and a lost order stops the call. The call prints the path of the record, a line for each order and rule (pass or NOT MET, and NOTE after a rule that gives a note), and at the end End: ... with the next command or STOP: ... with the reason.

resolve and unlock¶

resolve writes your decision on one order, offline and under the site lock, in one synced line: in the record, or, for a record of another runner, in older_decisions.jsonl of its site. The cases and options are on Resolving an order, and a stale lock; any other case is refused. For example, --unreadable takes an open order whose last stop is result_error, after two calls 10 minutes or more apart got an answer that could not be used, or two calls 24 hours or more apart got that stop.

unlock is offline. It removes the holder file of the site lock left by host NAME, after you have checked that no call runs there. It is refused if the holder names another host, or a live process on this host. Each unlock is written to ~/.local/state/qdevices/unlock.jsonl.

runs, jobs and usage¶

They read records only: the records folder of the app, the older_records folders of the config, and any record or folder given as PATH, also in the format of other runners (Manifests and records). They read a record of another runner with the decisions of resolve on its orders. A record, folder, PATH or file of decisions that cannot be read gives a line with its path and its error. usage leaves such a record out of its totals; without its decisions, the orders show and count as the record has them. usage says so on that line.

Manifests and records¶

Write a manifest to say what to send. The app writes a record of what was sent and what came back. The app never changes a manifest, and you never change a record.

The layout pin¶

Run qdevices check euroqexa --live --manifest FILE. It prints the layout of the machine and the line that pins it, "layout": {"layout_sha256": "...", "qubits": N, "pairs": M}: put that line in the manifest. The dry run compares the pin with the saved read (with no read, only its form), and a live call with its own read. Another layout fails the check, and nothing is sent (Euro-Q-Exa (LRZ)); qubits and pairs are then printed. When the machine has changed, a text may act on other qubits: read it again, check the texts against the new layout, then pin it. A record that has sent jobs cannot go on with a changed manifest (send in Commands).

layout_sha256 is the SHA-256, in hex, of one UTF-8 text: qubits=N;pairs=, then each coupled pair once as a-b, the lower index first, the pairs sorted and joined by commas. For 3 qubits coupled 0-1 and 1-2: qubits=3;pairs=0-1,1-2.

The records¶

Each run has its records in ~/.local/share/qdevices/records/<site>/<run>/, one run_<UTC>.jsonl each. <run> is the run key of the manifest, or the name of its folder. Each event is one JSON line, synced to disk before the next request (Live runs).

A line that was cut (for example by a crash), or is not UTF-8, is passed over. A resume prints each cut line as a NOTE, with the job id it holds, which may be cut too. The resume line keeps them in cut_lines: line, text (the first 120 characters), job_id and job_id_may_be_cut.

resume

at the start of each later call, with the rules file (The rules file in the record)

The reads¶

qdevices check SITE --live stores each read in ~/.local/share/qdevices/reads/<site>/read_<UTC>.json, through the token filter (Tokens). A read of Euro-Q-Exa also holds layout_sha256 and pairs beside qubits; a read of VLQ holds status, from the status file of the site (VLQ (IT4Innovations)). The list of machines of Euro-Q-Exa (a check without --manifest) is stored as list_<UTC>.json; the dry run does not take it.

In records and reads, a number that is not finite is written as the text "NaN", "Infinity" or "-Infinity", so each line and each read is standard JSON.

Records of other runners¶

Give the record or its folder to qdevices runs or qdevices usage, or list it in older_records of the config (Configuration). Listed records also count in the budget and the open-order check of a send to their own site. A record of another site in a listed folder is passed over. A record whose site cannot be told counts for each site that lists it.

  • In the records folder of the app, the app reads only its own records (run_<UTC>.jsonl).

  • Below a folder of older_records or a PATH, it reads the files named run*.jsonl, and every other .jsonl file whose first line is a start line. Give any other record by its own path.

  • One .jsonl file below the folder that cannot be read (no read permission, a broken link, or a first line longer than 1 MiB) makes the whole folder unreadable, even if it is not a record. A call that sends to its site is then refused (Commands).

  • Each record counts once, by its real path. Two copies in two folders count twice: list each record once.

  • An expired line of another runner (the site does not know the job) makes an order with no result final. It then counts at job_seconds_limit.

The app never writes a record of another runner. A decision of qdevices resolve on it (Resolving an order, and a stale lock) goes to ~/.local/share/qdevices/records/<site>/older_decisions.jsonl, as a resolved line that names the record by the SHA-256 of its first line and of the lines read (start_sha256, lines, lines_sha256), the job id (decided_id) and its path. The app adds the line when it reads the record while the order is as decided on, also for a copy that starts with the same lines. The file of decisions is never read as a record.

Rules¶

Give the rules of an experiment in a Python file, with qdevices send ... --rules FILE. A rule decides whether a run goes on. The generic rules of the app always run too.

qdevices send examples/euroqexa-three-jobs/manifest.json --live --max-order 1 --rules examples/rules_bell.py
qdevices send examples/euroqexa-three-jobs/manifest.json --live --resume RECORD --max-order 3 --rules examples/rules_bell.py

Warning

A rules file runs with your rights and can read the rest of the environment. The token variable is already deleted when the file is imported. Give only a file you have read.

With

Each gets plain dicts (no site object, no token) and answers with a verdict:

{"rule": "bell", "passed": True}
{"rule": "bell", "passed": False, "reason": "00 and 11 in 0.31 of the shots"}
{"rule": "pick", "passed": True, "skip": [4, 5]}

  • A verdict that does not pass stops the run, with exit code 2. Its reason is in the record.

  • skip names orders not yet sent: they are never sent in that record. An order that was sent, or that does not exist, stops the run.

  • A failed verdict: a function that raises, an answer that is not a verdict, a key that is not a text, or the key self.

  • Any other key is kept in the rule line, but not a key the line already has (event, utc, app, site, machine, project, point, order, and on VLQ lexis_project and resource). A note is also printed, as a NOTE line after the line of the rule.

  • At before_call, before_job and after_result, every generic rule and your rule must pass. Your on_refusal replaces the generic one, so an experiment can let a refusal go on.

On Piast-Q, qubit 0 is the leftmost character of each key of counts: element i of a shot is qubit i (release 1.15.0 of the maker’s client library), and the app joins the shot in that order. On Euro-Q-Exa, as measured with this app and not published by LRZ, a key reads q[n-1] … q[0], so q[0] is the rightmost character: a job with H on q[2] varied only the leftmost. The example file¶

examples/rules_bell.py stops the run if a Bell job gives the two even outcomes in less than half its shots:

"""An example rules file: stop the run if a Bell job gives the two even outcomes in less than half its shots.

A rule gets plain dicts and answers with a verdict. A verdict that does not pass stops the run. Use it with:

    qdevices send examples/euroqexa-three-jobs/manifest.json --live --max-order 3 --rules examples/rules_bell.py
"""


def after_result(job: dict, result: dict, state: dict) -> dict:
    """The verdict on one result: a Bell job passes when 00 and 11 hold at least half of its shots."""
    if not job["name"].startswith("BELL"):
        return {"rule": "bell", "passed": True}
    counts = result["counts"]
    even = counts.get("00", 0) + counts.get("11", 0)
    share = even / job["shots"]
    return {"rule": "bell", "passed": share >= 0.5, "share": share,
            "reason": f"00 and 11 in {share:.2f} of the shots, below 0.5"}

Nothing is cancelled¶

  • The app has no cancel call. If you must, cancel a job at the site with its own tools. Then, if the record shows the order as lost, record what became of it with qdevices resolve (below).

  • Ctrl-C, SIGTERM, SIGHUP and a wait time-out end the call with a “stop” line. The job runs on at the site. Collect it with qdevices send MANIFEST --live --resume RECORD. After an interrupt the call prints that command and Under way at the stop: order N (NAME), job ID. An error of the program (exit code 3) prints that line too.

  • A signal set to ignore stays ignored, so nohup works. The screen never ends a live call: a closed pipe or terminal is passed over.

  • Keep the machine awake (caffeinate -i on macOS). A sleep inside a request leaves a lost order.

One live call per site, from one host¶

send, check --live, resolve and unlock take the site lock, ~/.local/state/qdevices/<site>.lock.

  • A second live call on the site from this host is refused while the first runs: wait for it to end.

  • send takes the lock before it reads any record. resolve reads the record to learn its site (for a record of another runner, the site whose older_records read it), takes the lock, reads it again and decides under the lock.

  • The lock is an exclusive flock and a holder file <site>.holder (host name, pid, start time), as a cluster file system can grant a flock on each node with no error. A holder of another host refuses the call: check that host, then give qdevices unlock SITE --host NAME. A holder of this host whose process has ended is cleared. With no flock or no holder file, the call is refused: use a host whose home folder has flock.

  • Drive one site from one host. A laptop and a login node have different home folders and do not see each other’s lock or records. A resume that sends is refused on another host than the one that started the record. A resume without --max-order still collects there.

  • The lock covers this app only: no other tool may send to the site during a live call. Records of another runner count in the budget and the open-order check only when listed in older_records (Configuration).

  • Keep the clock of the host synchronised (NTP). The records, job times and time rules read it.

Tokens¶

  • The token is read once from one environment variable (MQSS_TOKEN, LEXIS_TOKEN, PCSS_API_KEY). The variable is then deleted from the process environment, before a rules file is imported (Rules).

  • The app reads no token file, and never stores or prints a token.

  • Never type the token on the command line. Use set +x; export NAME="$(cat FILE)": then it is not in your shell history or a trace.

  • The token goes only to the fixed addresses of the site, with no redirect. No flag and no environment variable moves them.

  • A filter cleans every record line, error, downloaded log and traceback. It takes out the token and the VLQ envelope passwords of the call (each password raw and in base64), each whole, in JSON form and by every start and every end of 8 characters or more; any text in the form of a JWT; the value of USER_JWT_PWD (the envelope password in the environment of a VLQ job) in any form; and Fernet text and its base64 form.

The generic rules check the shots, the budget and more before each job, and the result after it (Rules). The budget counts a lost or open order at job_seconds_limit, so the sum is an upper bound (Billing and usage).

How the text is written¶

examples/qrisp/qasm2.py reads Qrisp’s own circuit data and writes one line per instruction. It does not use Qrisp’s text export (to_qasm2, qasm, to_qasm3 of QuantumCircuit), as in Qrisp 0.9.10 that export hands the circuit to a package of another framework.

qc = qv.qs.compile()        # the circuit of the session of the variable qv
qc.measure(qc.qubits)       # every qubit into its own classical bit, in order
qc = qc.transpile()         # break composite gates (QFT, swap, cp) down
text = to_qasm2(qc)         # examples/qrisp/qasm2.py

The text has one register q of all qubits and one register c of all classical bits, and only gates of the original qelib1.inc. It is not optimised and no layout is chosen: the site does that. Hamiltonian simulation is what the quantum computer does: it applies the evolution of a physical system to its qubits.

1. The task: apply \(e^{-iHt}\)¶

The Schrödinger equation, with \(\hbar = 1\), is

\[i\frac{d}{dt}|\psi(t)\rangle = H|\psi(t)\rangle .\]

For a Hamiltonian that does not depend on time, the solution is

\[|\psi(t)\rangle = e^{-iHt}|\psi(0)\rangle .\]

In the eigenbasis of \(H\), with \(H|E_k\rangle = E_k|E_k\rangle\), each component only gains a phase:

\[|\psi(t)\rangle = \sum_k c_k\, e^{-iE_k t}\, |E_k\rangle .\]

The dynamics come from differences of energies. And the energies are written in phases.

For \(n\) qubits, \(H\) is a matrix of size \(2^n \times 2^n\). A gate-based quantum computer such as Euro-Q-Exa does not apply such a matrix directly: it offers one-qubit and two-qubit gates. The task is possible when \(H\) is a sum of terms that each act on few orbitals or spins, \(H = \sum_j H_j\), as the Hamiltonians here are, because the exponential of each term is a short circuit. So we build \(e^{-iHt}\) from those short circuits (Lloyd).

2. The model, and its exact answer¶

Three qubits in a line, with

\[H = \frac12\sum_{k=0}^{1}\left(X_k X_{k+1} + Y_k Y_{k+1}\right).\]

Call a qubit in \(|1\rangle\) an excitation. One term moves an excitation to the neighbouring qubit, and gives zero on \(|00\rangle\) and \(|11\rangle\):

\[\tfrac12(XX+YY)\,|01\rangle = |10\rangle .\]

So the number of excitations never changes. With one excitation the state lives in three dimensions, and there \(H\) is

\[\begin{split}\begin{pmatrix}0&1&0\\1&0&1\\0&1&0\end{pmatrix}, \quad\text{with eigenvalues } 0, \pm\sqrt2 .\end{split}\]

Expand the start in the eigenvectors \((1,\sqrt2,1)/2\), \((1,-\sqrt2,1)/2\) and \((1,0,-1)/\sqrt2\), with \(E=\sqrt2,-\sqrt2,0\). The start \((1,0,0)\), the excitation on q[0], has components \(\tfrac12,\tfrac12,\tfrac1{\sqrt2}\). Each gains its phase, as in Section 1. Adding them gives the amplitudes \(\cos^2\frac{t}{\sqrt2}\), \(-\frac{i}{\sqrt2}\sin(\sqrt2t)\), \(-\sin^2\frac{t}{\sqrt2}\) on q[0], q[1], q[2].

The share of each outcome is the square of its amplitude. A key reads q[2] q[1] q[0], as the machine returns it:

\[P_{001}(t)=\cos^4\frac{t}{\sqrt2},\qquad P_{010}(t)=\tfrac12\sin^2(\sqrt2\,t),\qquad P_{100}(t)=\sin^4\frac{t}{\sqrt2}.\]

At \(T=\pi/\sqrt2\) the phases \(e^{\mp i\sqrt2T}\) are both \(-1\), so the state is \(-|100\rangle\): the excitation is on q[2] in full. At \(2T\) it is back on q[0]. Chains of equal couplings do this exactly only at two and three qubits (Christandl et al.). 3. Split the exponential: product formulas¶

Write \(H = A + B\), with \(A\) on q[0], q[1] and \(B\) on q[1], q[2]. Each part is easy: a short circuit (Section 4). But they do not commute, \([A,B]\neq 0\), so \(e^{-i(A+B)t} \neq e^{-iBt}e^{-iAt}\).

For a short time \(dt=t/N\) the difference is small, and that is the idea of a product formula. \(N\) steps of

  • order 1: \(U_1(dt) = e^{-iB\,dt}\,e^{-iA\,dt}\), with an error of order \(dt^2\) a step;

  • order 2: \(U_2(dt) = e^{-iA\,dt/2}\,e^{-iB\,dt}\,e^{-iA\,dt/2}\), with an error of order \(dt^3\) a step.

These are also called Trotter steps. Expanding gives \(U_1(dt)=e^{-iH\,dt}+\tfrac12[A,B]\,dt^2+O(dt^3)\), so the commutator sets the first error; the symmetric form of order 2 cancels it. A product acts from the right, so in \(U_1\) \(A\) acts first.

Over \(N\) steps the errors add at most, so the total falls as \(1/N\) at order 1 and as \(1/N^2\) at order 2 (Suzuki). Its size is bounded by the commutators of the terms: pairs at order 1, nested commutators at higher orders. Terms that commute add nothing, so the number of terms alone does not set it (Childs et al.). The bound is for the worst state; a given state can do better.

4. One bond as gates¶

We need \(e^{-i\frac{\theta}{2}(XX+YY)}\). Here \(R_x(\theta)=e^{-i\theta X/2}\), \(R_z(\theta)=e^{-i\theta Z/2}\), and CX flips its second qubit when its first is 1. With \(A=\tfrac12(XX+YY)\) the bond is \(e^{-iA\theta}\), so \(\theta\) is the time of that step: \(dt\) or \(dt/2\). \(XX\) and \(YY\) commute, so no further split is needed. Two identities do the rest.

  1. A CX moves a Pauli operator from one qubit to two: \(\mathrm{CX}(X\otimes I)\mathrm{CX} = X\otimes X\) and \(\mathrm{CX}(I\otimes Z)\mathrm{CX} = Z\otimes Z\). So cx a,b; rx(θ) a; rz(θ) b; cx a,b is \(e^{-i\frac{\theta}{2}(XX+ZZ)}\).

  2. A rotation changes the basis: \(R_x(-\tfrac{\pi}{2})\, Z\, R_x(\tfrac{\pi}{2}) = Y\), and \(X\) stays \(X\). So with \(R_x(\pi/2)\) on both qubits before and \(R_x(-\pi/2)\) after, \(ZZ\) becomes \(YY\).

That is 2 CX for a bond. Neighbouring \(R_x(\pi/2)\) and \(R_x(-\pi/2)\) cancel, so a whole job needs them only at its two ends. The figure shows the job, one bond, and the general recipe for any Pauli term. The cell checks the bond against the matrix exponential.

6. What came back from the machine¶

The eleven jobs went to Euro-Q-Exa in one run on one evening, through the app qdevices, each with 1000 shots (CONTROL with 100). It shows how much of each answer survived that evening, not how good the machine is. The site compiles each text to the machine’s own gates, r and cz, and places it on its qubits. The record does not hold the compiled circuit, so what follows about the compile is read on the job pages of the portal.

A shot is one run of the circuit, ended by one measurement of every qubit; its key is the bits that come back. Readable, as set before the run: the ideal top key is the top of the counts and at least twice the next wrong key.

Read the table from the top. perfect is what a perfect machine gives for that text. read is the share of all shots. kept and checked come from the conservation check below.

CONTROL has no evolution: only the X gate and the readout. It reads 001, so q[0] is the right-hand character of a key. A reversed reading would look like no transfer at all.

MAIN is the job of Section 5, and the result this tutorial is built on. The excitation arrives: 100 is the top key by far. The perfect share is 0.970, so most of the loss is the machine’s, not the formula’s.

REPEAT is the same text as MAIN, sent again about 12 seconds later. One number from one job says little until you know how far a second job of the same circuit lands from it, so a repeat is the first check of any measurement. The two differ by 0.020. Shot noise alone, at 1000 shots each, gives a difference of about 0.021, so they agree as far as 1000 shots can show. One pair, 12 seconds apart, says nothing about how the machine drifts over minutes, hours or days. \(N = 1, 4\) and \(8\) ran about three minutes after \(N = 2\), and no repeat spans that gap.

The conservation check. Every step keeps one excitation, so a key with another number of 1s is a machine error, never an error of the formula. kept is the share of shots that pass, and checked is the answer among those. The check removes one readout flip in every case. It cannot remove an error that keeps the number of excitations, such as a wrong angle on a whole bond, so it is shown beside the raw reading, never in its place. The same check is used in chemistry, where the number of electrons is conserved (Section 10).

ZERO is the MAIN text without the X gate. With no excitation \(H|000\rangle = 0\), so a perfect machine gives 000 at any \(t\) and any \(N\), with no error of the formula at all. Here the answer is known exactly, so its reading shows what the compiled gates and the readout cost. It reads well below CONTROL, so gates did run, and the circuit that ran has all 10 CZ. Only 000 has no 1s, so here checked is 1 by construction.

QRISP has twice the two-qubit gates of MAIN in its text, and reads no lower (0.696 against 0.641 and 0.661). A text is a request, not what runs: the job page on the portal shows the circuit that ran, under Executed Circuit. For QRISP it has 10 CZ, as for MAIN: the site’s compile merged the four two-qubit gates of each bond into two. The two-spin example ising2 shows this more sharply: at 5 and at 16 Trotter steps it read the same, and both jobs ran with 2 CZ, as all their steps are one two-qubit block.

HALF and BACK follow the excitation in time. At \(T/2\) the middle key leads, and at \(2T\) the start key leads again. BACK evolves forward only, so no gate meets its own inverse. A compile could still shorten it: its product is close to the identity on all eight states, as the exact evolution at \(2T\) is the identity, and it equals three bonds with small angles. It reads close to STEPS4, with the same 18 two-qubit gates in its text (0.476 against 0.474, where shot noise alone gives about 0.022; kept 0.604 against 0.572). It keeps far fewer shots than STEPS1, with 6 (0.604 against 0.820), and its executed circuit has all 18 CZ: it was not cut to three bonds.

This is the main result. At \(N=1\) the formula itself is wrong: a perfect machine gives only 0.508. At \(N=2\) the formula is nearly right and the circuit is still short, and the reading is the highest of the four. At \(N=4\) and \(N=8\) the formula is close to perfect, but the reading falls. Each step adds gates, which fits the fall; one run cannot separate this from other causes. The best number of steps is set by both errors together. An experiment on two transmons, on the transverse-field Ising model, shows the same kind of maximum at a finite number of steps (Salathé et al.). On the same XX model, Smith et al. state the trade-off, measure the loss with each added step, and use the same conservation check.

That fall also tells us something about the compile. This model is free fermions (Section 8). For three sites every product of its bonds equals three bonds with suitable angles, at any \(N\): 6 CX in all (Kökcü et al.). The compile did not find that form: each STEPS job ran every two-qubit gate of its text (34 CZ for STEPS8), and the reading falls with \(N\).

Key 100 read 0.84 of its perfect share and key 010 only 0.58. The simple model of Section 7 does not do this, and one job cannot say why.

8. From three qubits to atoms and molecules¶

The path carries over; the shortcuts do not. Electrons in an atom or a molecule, with the nuclei held fixed and a finite set of spin orbitals, are described by

\[H = \sum_{pq} h_{pq}\, a_p^\dagger a_q + \frac12\sum_{pqrs} g_{pqrs}\, a_p^\dagger a_q^\dagger a_r a_s ,\]

where \(a_p^\dagger\) puts an electron in spin orbital \(p\). The numbers \(h\) and \(g\), with \(g_{pqrs}=\langle pq|sr\rangle\), are integrals that a classical code computes.

With one electron, or many with no second sum, the problem stays free-fermion: an \(M\times M\) matrix, which a classical computer diagonalises in time polynomial in \(M\). That is why the chain has a closed form and fits 6 CX. The second sum couples the electrons. An exact classical solution then works in a space of size \(\binom{M}{n}\), for \(n\) electrons in \(M\) spin orbitals: about \(10^{29}\) for 50 in 100. \(M\) qubits hold that space, which is why the method is studied. Classical methods treat many molecules well. A broad study of ground-state energies found no evidence so far of an exponential quantum gain across chemical space, and calls a relevant system with strong evidence an open question. It did not study other tasks and does not rule out smaller gains (S. Lee et al.).

Step 1, to qubits. Let qubit \(p\) read 1 when spin orbital \(p\) is full. The Jordan-Wigner transformation writes \(a_p = \left(\prod_{k<p} Z_k\right)\tfrac12(X_p + iY_p)\). Electrons anticommute, \(a_pa_q=-a_qa_p\). Operators on different qubits commute, so the \(Z\) string supplies the sign: it counts, modulo 2, the electrons in the orbitals below \(p\). So a term can reach across many qubits. For neighbouring orbitals the \(Z\)s cancel:

\[a_k^\dagger a_{k+1} + a_{k+1}^\dagger a_k = \tfrac12\left(X_k X_{k+1} + Y_k Y_{k+1}\right).\]

That is the bond of this tutorial. The chain above is one electron hopping along three orbitals in a line. Its \(3\times3\) matrix is the Hückel matrix of the three π orbitals of the allyl radical, in units of \(\beta\), with \(\alpha\) set to zero. The radical has three π electrons; here we follow one, and with no second sum each moves on its own. Between orbitals that are not neighbours, the \(Z\)s stay. The cell checks both.

Step 2, the terms. The second sum of \(H\) adds terms such as \(Z_pZ_q\) and \(X_pX_qY_rY_s\). Their number grows as the fourth power of the number of spin orbitals. Each is one Pauli term, so each uses the general recipe of the figure, and they are split by the same product formulas, with the same trade-off of Section 6.

Step 3, what we get from it.

  • Dynamics: evolve a prepared state and measure, as here: how charge moves, or how a system answers a sudden change.

  • Energies: phase estimation runs a controlled \(e^{-iHt}\) and reads the phase \(e^{-iEt}\) of Section 1 into a register, which gives the energy \(E\) (Abrams and Lloyd; Aspuru-Guzik et al.). An error in \(e^{-iHt}\) becomes an error in \(E\). It returns \(E_k\) with probability \(|c_k|^2\), the \(c_k\) of Section 1. So the state prepared first must overlap the state wanted; for a large molecule that is a problem of its own.

  • Other algorithms use it as a part: linear systems, thermal states, adiabatic state preparation. Card P06 of the Quantum Algorithmic Primitives Atlas lists them. The Quantum Algorithm Zoo (Jordan) has an entry on this routine, which lists Qrisp among its implementations.

Here is the hydrogen molecule, emulated, with the two-qubit Hamiltonian of Qrisp’s ground-state page: the same trotterization, inside phase estimation. Its numbers match H2 in the minimal basis STO-3G at 0.735 Å: 4 spin orbitals, which its symmetries reduce to 2 qubits. Energies are in hartree, for the electrons alone. The repulsion of the nuclei adds 0.720, so the total is -1.137.

9. The whole curve of H2¶

So far the molecule has one bond length. Now we hold the nuclei fixed at many bond lengths, and compute the energy at each. The result, energy against bond length, is the potential energy curve, the picture chemists recognise for a bond. Its minimum gives the equilibrium length of the bond. The depth of its well is close to the energy it takes to break the bond, but larger by the zero-point vibration of the nuclei, which fixed nuclei leave out: about 6 kcal/mol for H2 (from the constants of the NIST WebBook). Its far end must reach the energy of two separate atoms, and not every method gets there.

The phase estimation below is emulated: a laptop computes what a perfect quantum computer would do, and nothing is sent to a machine. Its circuits are far longer than anything the machine of Section 6 read: 9248 two-qubit gates at each bond length in this form, against at most 34 in the texts sent there. A laptop also solves this molecule directly, and much faster, so nothing on this page gains over a classical computer.

What exact means for each method. Each one works on the same equation: the Schrödinger equation of the electrons, with the nuclei held fixed (the Born-Oppenheimer approximation) and no relativity. They differ in the method and in the basis. A basis is the finite set of functions, centred on the nuclei, from which the orbitals are built. STO-3G is a minimal basis: one function on each atom, a fixed sum of 3 Gaussians. cc-pVQZ, the largest here, has 30 on each atom.

  • Restricted Hartree-Fock puts both electrons in one orbital. It is the start of our phase estimation. In any basis it is an approximation.

  • Full configuration interaction (FCI) solves the Schrödinger equation exactly within a basis: in the words of Szabo and Ostlund (p. 234), “exact within the subspace spanned by the one-electron basis”. So each basis has its own FCI energy. In STO-3G, for the ground state, FCI comes down to a \(2\times2\) matrix, which molecule.py builds with NumPy alone. exact_chemistry.py uses PySCF for the larger bases, and this page reads its stored numbers.

  • Phase estimation in STO-3G reads the levels of the same \(2\times2\) matrix, on a grid of energies and through a product formula. With a finer grid and more steps it closes on FCI in STO-3G, and on nothing better. A single reading can fall below FCI: that is the grid, not a better result.

  • The published values (Pachucki) solve the same equation with no limit from a basis, as they are extrapolated to a complete set. To every digit we print they are exact for this equation, not for the real molecule, and they are computed, not measured. Here they are the benchmark. Sims and Hagstrom agree with them to better than \(4\times10^{-12}\) hartree at every length both list, from 0.21 to 3.18 Å.

Molecule(length).terms gives the five coefficients of the two-qubit Hamiltonian at any bond length. These are errors of total energies. Chemical accuracy usually refers to energy differences against experiment, within 1 kcal/mol (Motta and Rice). Agreement with FCI in a fixed basis is another thing, which Motta and Rice call algorithmic accuracy. Phase estimation in STO-3G could reach that and still lie about 23 kcal/mol from the published energy at 0.7414 Å.

For a classical computer these two electrons stay easy. C(M, 2) is the \(\binom{M}{n}\) of Section 8 for two electrons, at most 7140 here, before symmetry makes it smaller: in STO-3G the 6 states become the \(2\times2\) matrix. PySCF solved all five bases at all 24 bond lengths on one laptop in one to five minutes. This molecule is a place to check the method against known numbers.

Experiments have traced the curve of this molecule in a minimal basis. Lanyon et al. worked in STO-3G, with 2 photonic qubits and 20 bits of iterative phase estimation, which reads one bit at a time on one control qubit. A problem this small let them set each power of the evolution directly, “by re-encoding the same number of gates”. They do not expect that for larger molecules. They also encode “exact eigenstates, obtained via a preliminary calculation on a classical computer”. O’Malley et al. worked in STO-6G, with 2 superconducting qubits for a variational method and 3 for Trotterised iterative phase estimation. They write: “we are able to implement only a single Trotter step, which is not enough to achieve chemical accuracy.” Their chemical accuracy is measured against the exact energy in that basis, which is the algorithmic accuracy above. So the limit of the basis applies to both.

The budget¶

Before each job the rule budget adds up:

  • the measured seconds of every result in every record of the site and project, and in older_records;

  • job_seconds_limit for each order of unknown time: a lost or open order, a failed job, an order with no result that an older runner wrote as expired, and a result with no measured seconds;

  • job_seconds_limit for the job about to be sent.

Above budget_seconds, the job is not sent and the run stops. Raise budget_seconds only if your award allows it. The sum is an upper bound of what the app has used, not the charge of the site.

  • Measured seconds are the first number of 0 or more among seconds, device_seconds (older runners) and wall_seconds: a time below zero is no measure, in an older record too. wall_seconds (job request to result) is a number when the call that sent the job also collected it, else null. So a result with no seconds (for example a Euro-Q-Exa result whose time stamps cannot be read, or give a time below zero) counts its wall seconds, or else job_seconds_limit. jobs, runs and usage show them as measured, and resolve --over-limit judges on them. The rule job_time reads seconds only, so it stops at such a result.

  • 0 seconds: a refusal, a job never submitted, and an order resolved with --none. But an order resolved as still New, or one whose job id no URL can hold, counts at job_seconds_limit: its job may yet run.

  • After --over-limit, --expired, --unreadable or --gone: the counted_seconds of the resolved line, the job_seconds_limit of the config at the decision. A later change of the config does not change them. For a record of another runner, a result it writes later counts with its measured seconds (Resolving an order, and a stale lock).

  • Other members: the app counts only the records it reads. LRZ counts the use of every member of a project against one budget (General information on the Euro-Q-Exa user operation). Set budget_seconds with the use of the other members in mind.

A result above the job time limit¶

The seconds the site reports can hold a wait at the site, cause not known. On Piast-Q, a result collected by a later call holds the wall seconds up to that call. The rule job_time then stops the run, and the result counts with all its seconds, so the rule budget can stop every later send of the project.

When you find that the time is such a wait, give qdevices resolve RECORD ORDER --over-limit. The result then counts at job_seconds_limit; its measured seconds stay in the record, and runs and usage show both. Decide it for each order: a job that did run that long would then count too little.

qdevices usage¶

qdevices usage [PATH ...] gives the totals by site and project (Commands). Seconds counted put the seconds of a decision of --over-limit, --expired, --unreadable or --gone in place of the measured ones. Neither is the sum of the budget: both leave out each order of unknown time, and an order resolved as still New. The totals come from the records found, not from the sites. To count older records, give their folders as PATH, or list them in older_records.

usually daily, at night, about 1.5 hours, at times several hours, and it can affect running jobs (LRZ). A way to see the last one is under development (portal FAQ). LRZ’s page Euro-Q-Exa regular user operation announces an upgrade that offers 150 qubits

Compiling and no_modify¶

Without no_modify, the MQSS pipeline of the site compiles and optimises the circuit (portal FAQ). The record does not hold the compiled circuit: the job page of the portal shows it under Executed Circuit, and the logs of a failed job in its Note field (portal FAQ).

"no_modify": true asks the site not to compile. The circuit must then be in the native gates (r, cz, measure, barrier) and on coupled pairs. The dry run checks the gate names against a saved read (qdevices check euroqexa --live --manifest FILE). The LRZ training material of the pilot phase compiles a circuit locally for EQE1, with a chosen qubit layout, and sends it with no_modify (its example 03). The MQSS adapter guide notes: “The transpilation at user end may not be supported for some backends.”

Pairs. With no_modify, the dry run and a live call check each two-qubit gate against the cz loci of the read. A pair listed in neither order fails, and nothing is sent. A pair listed only the other way round is a note. A note also says when the check was not made: for a text it cannot read (for example several quantum registers, a range of qubits, or physical qubits), or a read with no readable cz loci.

Layout. The pairs of the read are the layout (The layout pin). When the layout differs from the pin, a live call stops before its first job (a stop check, with the qubits and pairs then and now). Without the pin there is no such check; the read line still holds the layout.

Shots times gates¶

A job may hold at most 3,000,000 shots times gates, summed over the circuits of a batch (LRZ). The app sends one circuit a job, and counts the gates in the text it sends:

Statement

Counts

each application of a gate, measure, reset

once

a statement on whole registers, such as h q; or measure q -> c;

once for each qubit of the register

a call of a gate that the text defines (gate NAME ... { ... })

the operations of its body, calls in it in turn, 32 deep at most

a statement under if (...)

as above, 32 deep at most

barrier, declarations, includes, qreg, creg

not at all

The dry run gives the gates and the shots times gates of each job, and fails a job above the limit. Before each job the rule shots_times_gates checks the same: above the limit it stops the call with exit code 2, and nothing is sent for that job (Rules). A job at the limit goes. Above it, use fewer shots or a shorter circuit; a record that has sent jobs cannot go on with a changed manifest (send on Commands).

Some texts cannot be counted: for example a modifier such as ctrl @, delay, a physical qubit such as $0, a range of qubits, nesting deeper than 32, or a gate that calls itself. The dry run then shows gates not counted with a note, and the rule passes with a note: check the job yourself against 3,000,000. Without no_modify the site’s count can be higher than the app’s; the dry run notes it.

Times¶

The site writes timestamp_submitted, timestamp_scheduled and timestamp_completed with no zone. They appear to be local time in Germany (two hours ahead of UTC in summer, in the release gate). The app reads them as UTC+2 from 01:00 UTC on the last Sunday of March to 01:00 UTC on the last Sunday of October, and UTC+1 at any other time; in the hour that the October change repeats, it takes the reading nearest its own time of the job request. The result line keeps the stamps, and adds scheduled_utc, completed_utc and zone_check. With zone_check true, the seconds run from scheduled_utc to completed_utc. It is false when the record has neither time for the job, timestamp_submitted is more than 5 minutes from it, or a stamp cannot be read so or has two readings: the seconds are then the plain difference of the stamps, and could be one hour off. A difference below zero is no time: the seconds are then null, and the result counts as one with no seconds (Billing and usage).

Traps¶

  • An answer of HTTP 400 or 422 to the job request is a refusal only when its body has a word that starts with cz, pair, coupler, direction, locus, loci, qubit, no_modify, gate or native and ends there or with an s, in upper or lower case: gates is such a word, gateway is not. Any other answer with no job id, or no answer, is unknown (Live runs).

  • A 403 is not always a fault of the token. In the release gate a token that worked before and after got a 403 while the portal login failed with Internal Server Error; the cause is not known. Check the portal login before you make a new token.

  • In the release gate a Bell job in h and cx, sent for the site to compile, stayed WAITING for days while the machine was online with no job pending; the cause is not known. It came back after four days, never cancelled, with 100 of 100 shots and 342,011.9 s from scheduled to completed: not device time (inferred). The rule job_time stopped the order. Such a result counts at job_seconds_limit after qdevices resolve RECORD ORDER --over-limit (Billing and usage). euroqexa-one-qubit is also sent for the site to compile.

The token at the site. The VLQ service needs the token inside each job folder, in its own envelope (Fernet, with a key from a password of the job), and the envelope password in the job’s environment. So the token is at the site in a form the site can open: this is the scheme of the service. The app never writes the job’s environment to a record. By the public code of the service, the job script deletes the token file, user_token.enc, once it has read the token, and in any case when it ends.

The circuit¶

One OpenQASM 3 circuit per job, in native gates only: r (PRX), cz and move between a qubit and the resonator, and measure. Declare r and move as gates with an empty body (gphase(0)). VLQ does not compile or route, so register index i is the component of index i in the table of the init job of the day. No IT4I or maker page prints that table, and it can change with the calibration set. The example files vlq-bell and vlq-ghz take QB1 to QB24 at 0 to 23 and the resonator COMPR1 at 24 (a register of 25); after the init job the app checks each text against the table of the day (below).

The maker’s software that runs the job still checks it; the app does not make these checks. By the maker’s public defaults, move gates come in pairs, with no gate on the moved qubit and no other move on the resonator between the two. The maker’s server rejects a circuit estimated to take longer than the shortest T2 of its qubits times a server value, which is not published, and the release on VLQ is not published.

An order is two jobs¶

An init job (backend_init, in the init queue) writes two artefacts of the service, and the metered job (backend_run, in the compute queue) needs them. The app carries them as bytes. It reads one, iqm_target_attrs.pkl, with the restricted reader (below); no artefact goes through the standard loader. By the public service code an init job uses no device time, but HEAppE can book its classical node time (NumNodes x RunTime), which a site utilisation report may count. qdevices usage shows init jobs and their node time apart. Each new try after a stop makes another init job, which books node time.

The table of the day. After the init job, the app reads from iqm_target_attrs.pkl the index of each component, the qubits, the resonator, and the loci of cz and move. Before the metered job is made, it checks that r, prx and measure act on the index of a qubit, and that cz and move act on the index of a qubit, then of the resonator, on a pair the table lists as a locus of that gate.

A text that does not fit the table stops the call before the metered job is made, with a stop prepare at the step table. The init_done line lists each problem in table_problems, for example cz on indices 1 and 24: the table of the day has no index 24 (its size is 24). The order stays unsent. A resume with --max-order tries again, on the table of that day.

When the table cannot be read, the call prints a NOTE, the init_done line holds table_note with the reason, and the job goes with no check. The check also reads only a text with one quantum register, in plain statements; table_note says when the text was not checked.

The init_done line holds table: size (the number of components), resonators (the index of each) and sha256, the SHA-256 in hex of this UTF-8 text, with the names of the table:

{"index":{NAME:INDEX,...},"loci":{"cz":[[QUBIT,RESONATOR],...],"move":[[QUBIT,RESONATOR],...]},"qubits":[NAME,...],"resonators":[NAME,...]}

It is Python’s json.dumps with sort_keys=True and separators=(",", ":"). Each list is sorted; a locus is the two names in the order of the table, once for all implementations of the gate. The digest changes when another component sits at an index. No name of a component goes into the record.

The status file¶

Each read of the machine starts with the public status file https://quantum.heappe.it4i.cz/vlq-status.json, the address on IT4I’s Calibration and Health page. It needs no login, and gets no token. Its four flags are the rows of that page, UP or DOWN: QPU (QPU_status), QCCSW (QCCW_status), Internal Scheduler (queue_available) and Overall (total_status). The read and the read line hold status: flags (null for one not given), the timestamp of the file, and error when it cannot be read, else null.

The rule site_status (Rules) stops the call before its first job when a flag is false, with exit code 2 and a reason such as the VLQ status file shows QPU down. A file that cannot be read, or a flag that is not true or false, passes with a NOTE: it never stops a call by itself.

Results and times¶

  • The service returns pickles. The app reads them with a reader that maps every name to an inert stub, so nothing in them is imported or run. It refuses files above a size limit, and has caps on its walk.

  • Each result line holds calibration_set: the id of the calibration set the job ran on, as the canonical text of a UUID (lower case, with hyphens), from the fields calibration_set_id in results.pkl. It is null when the file gives no id, or two different ids; the result is kept. Jobs run on the set default unless another is named when the backend is made, and a set can be read by its id at https://extranet.it4i.cz/vlq-calibration/ (IT4I’s Calibration and Health page). The app names no set. When a new set is made is not published.

  • A result needs the counts in results.pkl and the key remote_hw_runtime of job.pkl, the device seconds. A value of it that is not a finite number of 0 or more is kept as null. With no counts, no remote_hw_runtime at all, or a file that cannot be read, the call stops at result_error and the order stays open. When two calls 10 minutes or more apart got that stop, qdevices resolve RECORD ORDER --unreadable makes the order final, counted at job_seconds_limit. A download that gets no usable answer (a redirect or an HTTP error of 400 or more, or no answer up to wait_seconds) also stops at result_error; then the two calls must be 24 hours or more apart (Resolving an order, and a stale lock).

  • HEAppE gives StartTime and EndTime with no zone, and does not publish its zone. They appear to be local time: in the release gate, in summer time, they were two hours ahead of UTC. The node_seconds of an init job are EndTime minus StartTime, so they may be one hour off across a change of the clocks. A time below zero is no measure: it is written as null and left out of the sum of usage.

Traps¶

  • A job that was created and not submitted is left as it is. SubmitJob is never called on a resume, and the record decides what becomes of a job that HEAppE shows as Configuring (Live runs).

  • An HTTP 4xx other than 401, 403, 408 and 429 to the upload of the circuit file is a refusal: the job was made and is never submitted, and the order is final. Any other failed request of the metered job is unknown (Live runs).

The job file¶

Each job file is a JSON object with the operation list of the broker:

{"number_of_qubits": 2, "quantum_circuit": [{"operation": "RXX", "qubits": [0, 1], "theta": 0.5},
                                            {"operation": "MEASURE"}]}

  • Angles are in units of pi: R takes theta in [0, 1] and phi in [0, 2], RXX theta in [0, 0.5], RZ any phi. The list ends with one MEASURE. The broker refuses a value outside its schema with HTTP 422; the dry run checks the same ranges offline.

  • The dry run also checks 1 to 20 qubits, the 20 data qubits of the PIAST-Q specification of PCSS, and 1 to 2000 operations, the limit of a circuit in the maker’s AQT Public API 1.1.1.

  • By that interface, the maker’s machines rewrite an R with theta at most pi/5 (0.2 here) as two rotations; whether Piast-Q does is not published.

Shots¶

Keep 200 shots a job, the limit the app holds, unless PCSS says otherwise.

  • No public PCSS page gives a limit. Release 1.15.0 of the maker’s client library caps a job on a machine at a customer’s site at 200 shots (a later pre-release allows 2000). LRZ gives 200 for its own machine of this maker (knowledge base for users of the AQT system).

  • The broker does not check the shots. A job above the limit is not refused, and can stay open with no answer: in the release gate a Bell job of 400 shots stayed New for four days. It blocked a new run until it was resolved as still New with qdevices resolve ... --none (Resolving an order, and a stale lock); the same circuit at 200 shots then ran in 182.8 s.

  • Set site_max_shots only when PCSS gives your award another limit in writing (Configuration). The dry run notes a value above 200.

The broker¶

  • Machine list. GET /machines gives the names only, with no state; the app does not read the queue count (GET /machines/queue-count). So “online”, in qdevices check piastq --live and the rule machine, means only that the name is in the list (Rules). The qubits of the read are the 20 that the app holds, not a read of the machine.

  • Connections. The troubleshooting text names the answer HTTP 429 max connections reached, with no number. The app keeps one connection in use. A 422 with an upstream 429 in the detail is not a refusal: a job request that gets it leaves a lost order, and a read of the state or result that gets it is a missed poll (Live runs).

  • Results. How long the broker keeps a result is not published: collect each job the same day. The answer code 4 with Unknown job. May be expired., whatever the HTTP status, ends the call with a stop result_expired. The order stays open (exit code 1). Resume once more, 10 minutes or more later. When two calls got that answer, qdevices resolve RECORD ORDER --expired makes the order final: never sent again, counted at job_seconds_limit (Resolving an order, and a stale lock). A result that is not a list of shots, each a list of bits, ends the call with a stop result_error, and the order stays open; when two calls 10 minutes or more apart got it, --unreadable makes the order final, counted the same way. A read of the result with no usable answer (a redirect or an HTTP error of 400 or more, or no answer or too many connections up to wait_seconds) also stops at result_error; then the two calls must be 24 hours or more apart.

  • A lost order. The broker has no published call that lists your tasks (PCSS client 0.2.2). Ask PCSS whether a task was made. Then give its id with qdevices resolve RECORD ORDER --job ID, or --none only when PCSS says none was made.
